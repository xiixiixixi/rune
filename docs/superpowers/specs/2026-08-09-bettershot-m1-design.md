# BetterShot 第一阶段改造设计

## 1. 目标与边界

本阶段完成总纲中的 M0（基线与工程纪律）和 M1（截图地基），让 BetterShot 从依赖系统命令的截图工具，变为基于 Apple 原生 ScreenCaptureKit 的轻量截图应用。

完成后，用户可使用区域、窗口、全屏和延时截图；区域选择由应用自己绘制；截图进入编辑器不会因大图而阻塞界面；默认快捷键不再依赖“辅助功能”权限；未获得屏幕录制权限时，应用会在首次截图时给出清晰引导。

本阶段不做录屏界面、在线更新、滚动截图、上传、历史检索、二维码和文字识别的功能扩展。这些功能保留现有源码或入口兼容性，但不会作为本阶段交付内容。

## 2. 交付方式

按以下顺序实施，每一步都可独立检查：

1. 建立测试目标、基础持续检查和改造前性能记录。
2. 新建 `CaptureKit`（采集核心）目录，并通过它获得屏幕、窗口和静态截图。
3. 将截图编排改为可取消的状态机，并用新选区界面取代系统命令的选区界面。
4. 让编辑器的缩略图和美化渲染在后台执行，主界面只负责显示结果。
5. 用 Carbon（苹果系统快捷键接口）登记快捷键，并保留设置页中的重绑定能力。
6. 隐藏录屏与视频编辑入口，保留相关源码但排除出本阶段的可见产品流程。

## 3. 截图架构

### 3.1 模块职责

新增的 `Sources/CaptureKit/` 只负责“取得像素”和“描述显示器”，不会直接打开编辑器、保存文件或显示通知。

| 文件 | 责任 |
| --- | --- |
| `CaptureEngine.swift` | 对外提供全屏、窗口、显示器和矩形截图的异步入口。 |
| `ScreenTree.swift` | 读取当前可截图的显示器与窗口，并转换为应用自己的轻量数据结构。 |
| `StillCapture.swift` | 封装 ScreenCaptureKit 单帧截图与短时预热缓存。 |
| `DisplayLayout.swift` | 在 AppKit（界面坐标）和像素坐标之间换算，并合并跨屏截图。 |
| `CaptureStateMachine.swift` | 用纯数据表达截图流程、取消和错误，不含界面代码。 |
| `TCCSupport.swift` | 检查屏幕录制授权状态，并提供一次性的用户引导信息。 |
| `FrameRecorder.swift` | 只建立未来滚动截图和录屏会用到的接口；本阶段不提供滚动截图功能。 |

现有 `Sources/Capture/ScreenCapture.swift` 变为兼容门面：外部调用者仍从这里请求截图，但不再启动 `/usr/sbin/screencapture`（系统截图命令）。`CaptureOrchestrator`（截图编排器）只负责倒计时、选择截图动作、交给编辑器或预览，不再处理底层像素取得。

### 3.2 截图数据

截图完成后，应用在内存中传递一份 `CaptureRecord`（截图记录），其中包含实际像素、屏幕缩放倍率、来源显示器和截图时间。文件地址不再是截图的唯一来源，而是保存或导出后的结果。

这样能避免“先写临时文件、再读回内存、再处理”的重复工作，也让 Retina（高分屏）像素倍率有明确归属。保存 PNG 时默认保留原始物理像素；设置项可在后续阶段增加 1 倍和 2 倍导出选择。

### 3.3 多显示器与区域选择

区域选择界面显示在鼠标所在屏幕。界面先取得一张冻结画面，再在其上绘制半透明遮罩、选区边框和尺寸提示。拖动时允许从任意方向开始；方向键可微调；按 Tab（制表键）轮换自由、1:1、3:4 与 16:9 比例；按 Esc（退出键）在任何阶段取消。

跨显示器拖选时，`DisplayLayout` 会分别取得每块屏幕的交集，再按全局位置拼成一张图。坐标换算和拼接算法必须是独立、可自动测试的纯函数。

### 3.4 状态与异常

截图流程使用以下单向状态：

`空闲 → 预热 → 选择区域 → 调整区域 → 确认 → 截图中 → 完成或失败`

状态机只接受“快捷键触发、鼠标拖动、确认、取消、超时、截图成功、截图失败”等事件。每一个状态都能响应取消；一次操作失败后回到空闲，不会遗留半透明界面、队列或临时文件。

首次请求截图时才检查屏幕录制权限。没有授权时，应用不会假装截图成功，而是显示一条解释“为什么需要权限”和“到哪里开启”的引导；启动应用与注册快捷键不主动弹权限框。

## 4. 编辑器速度与内存

为避免 5K 高分屏截图导致界面冻结，编辑器按三段工作：

`取得截图 → 后台生成缩略图与渲染结果 → 主线程显示`

缩略图使用 ImageIO（苹果图片解码框架）生成，最大宽度为 512 像素。背景、美化和标注合成进入专门的后台队列；用户看到的是可交互的编辑器和“处理中”占位，而不是卡住的窗口。

同一张截图的旧任务必须在新截图到达、编辑器关闭或用户取消时失效，避免后完成的旧任务覆盖新界面。编辑完成后应释放大尺寸像素引用，避免连续截图时内存持续累积。

## 5. 快捷键与产品裁剪

快捷键改用 Carbon 的 `RegisterEventHotKey`（系统全局快捷键登记接口），不再使用会要求辅助功能授权的事件监听。默认键位为：

| 动作 | 默认键位 |
| --- | --- |
| 区域截图 | Command + Shift + A |
| 全屏截图 | Command + Shift + S |
| 窗口截图 | Command + Shift + W |

原有设置页继续保存、启用、停用和重设快捷键；如果某个键位被系统或其他应用占用，应在该项旁边显示失败原因，且不影响其他快捷键。

本阶段菜单和快捷键中不再显示录屏入口。录屏引擎及视频编辑源码暂时保留，但不作为可触发功能，也不应阻塞截图应用的编译和启动。

## 6. 测试与持续检查

新增独立测试目标，优先覆盖最容易回归且无需真实屏幕权限的逻辑：

- 截图状态机：正常流程、取消、超时、重复触发和失败复位。
- 坐标换算：主屏、左侧屏、上下排列屏、高分屏缩放与跨屏矩形。
- 截图数据模型：像素大小、倍率、来源显示器和导出信息。
- 快捷键配置：默认值、储存、重设和冲突结果。

新增 GitHub Actions（GitHub 自动检查）工作流：每次提交时生成 Xcode 工程、编译应用并运行测试。签名、公证和发布流程留给下一阶段，避免在没有证书的公共检查中泄露或依赖私人凭据。

## 7. 验收标准

第一阶段以以下证据为完成条件：

1. 代码中不再以系统 `screencapture` 命令作为正常截图路径。
2. 区域、窗口、全屏和延时截图均能进入编辑或预览流程；取消不会留下界面。
3. 屏幕录制权限只在首次真正截图时引导；快捷键登记不要求辅助功能权限。
4. 高分屏截图保留物理像素，且双屏与跨屏的坐标测试通过。
5. 编辑窗口能先显示，再在后台完成大图缩略图和美化渲染；连续截图的旧任务不会覆盖新结果。
6. 测试和自动编译检查已加入项目，并能在装有完整 Xcode 的机器上执行。
7. 本机补装完整 Xcode 后，记录并回填空闲内存、截图到编辑器的耗时、5K 截图耗时和连续 20 次截图后的内存回落情况。

## 8. 已知环境限制

当前机器只有 Apple Command Line Tools（命令行开发工具），没有完整 Xcode，因此不能在本机生成工程、编译 macOS 应用或执行界面截图验证。实现期间仍会完成静态检查和可独立运行的逻辑测试；完整编译、双屏和真实权限验证必须在安装完整 Xcode 的 macOS 设备上补做，不能用“代码看起来正确”替代。
